# 更新後の履歴の判断の復旧

回答済みの Question は回答済みの履歴として残る。Questions と API は保存済みの
回答と回答時刻を保持し、merge / hold の操作を再表示しない。履歴の注記から
「Pending decisions」一覧へ移動できる。履歴があるだけでは操作の完了を証明できず、
保存済みの回答の取り込みが新たな操作を許可することもない。

修正版へ更新したら、通常の daemon / web scheduler を再起動する。既存の
task-chat sweep が、以前の版ですでに取り込んだ記録も含め、保存済みの移行境界を
一度に最大 64 件ずつ補正する。進捗は保存され、再起動後も続行する。
補正中に対象の境界は拡大しない。ストアの手編集・削除、再回答、PR のマージは
不要。受諾済みの要求、明示的な解決、配送済みの会話の本文は保持する。

残る inquiry は「Pending decisions」で確認する。対応する永続的な効果の受領記録が
確認できれば解決する。回答の配送済みフラグ、タスクの完了、所有者の不在だけを
完了証拠にはしない。効果不明のものには理由を付けて未解決のまま残す。
元の記録や移行 journal が読めない場合も、診断情報を残し、解決とは扱わない。
通常の対応で読取り・アクセスの問題を解消し、警告を消すために移行 journal を
削除・書換えしないこと。

元の所有タスクのチャットに、inquiry ID を指定して
`magi task control reconcile-decision <id>` を実行するよう依頼すると、既存の
永続的な証拠だけを再照合できる。未配送で所有者不明の履歴 inquiry は、権限のある
既存のチャットからも再照合できる。再照合は操作を実行せず、効果を確認できなければ
エラーを返して未解決を維持する。

所有者自身が残作業なしと確認した場合は、そのチャットから
`magi task control settle-decision <id> --reason <reason>` で理由を付けて明示的に
精算できる。これは所有者の判断を記録する操作であり、保存回答の再生、PR の
マージ、fallback 本文の公開、タスクの再開は行わない。所有関係を復元する場合は
確認できた元の関連付けを使い、配送先を推測しないこと。証拠か所有者の明示的な
精算が得られるまで、不確実な効果は判断待ちに残る。

## 一覧での完了条件と確認

`Pending decisions` は resolved 以外をすべて unresolved と数え、完了したものは
`Resolved history` に分ける。配送・既読・保存済み返信だけでは完了しない。
確定した効果の受領記録、または理由付きの明示的な精算が必要となる。
`Resolved` 自体は操作の適用を保証しないので、カードの `Outcome and status history`
から受領記録または精算理由を確認する。記録された要求と問い合わせ本文も展開できる。

`Awaiting owner` は入力待ち、`Queued` は要求記録済みだが効果未確認、
`In progress` は実行中。`Needs retry or result check` は未解決のままであり、
実行前失敗が証明された要求だけに同じ要求の再試行を案内する。それ以外は元の
所有チャット（所有関係がない場合は権限のある既存チャット）で再照合を依頼する。
表示やリンクを開くだけでは返信の再生・再試行・精算を行わない。
読込失敗時の一覧は前回の内容であり、一部読込不能の警告がある件数は部分的な件数となる。
