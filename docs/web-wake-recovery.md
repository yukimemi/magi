# スリープ復帰後の Web UI 応答停止の調査

## 基点と再現範囲

ランチャーが 2026-11-03T04:56:37Z に取得した基点は
`c53c77f99850dc17359c463ea27cd9ef40bdb1d1`。作業開始時の HEAD と一致することを
確認し、再 fetch や基点変更はしていない。この基点には既に visibilitychange、
pageshow、online の復帰処理がある。

報告画像は Brave/Chromium のネイティブな「ページが応答しません」ダイアログだった。
これはレンダラー停止の証拠であり、SSE 接続障害の証拠とは扱っていない。
以下は CDP と実際の headless Chrome を使った合成再現で、OS の休止や Brave 実機を
再現したものではない。

## 確認できた停止経路

参照リンク装飾は rAF の後に実行するタイマーへ依存していた。rAF を保留して
`referenceText` で 1,200 個の範囲を作り、`refreshReferences` を繰り返すと、
同じ範囲が世代番号だけを変えて配列へ追加され続けた。`flushReferences` はこの配列を
`shift()` で取り出し、古い世代を同期的に読み飛ばしていた。通信のバッチ制限は
無効項目の走査時間を制限していなかった。

| 条件 | 待機キュー | 更新通知の処理 | 装飾処理 | 最初のタイマー応答 |
| --- | ---: | ---: | ---: | ---: |
| 基点、20 回更新 | 25,200 | 20.9 ms | 372.4 ms | 69.9 ms |
| 基点、120 回更新 | 145,200（コード上の件数） | 完了時間未取得 | CDP が 30 秒でタイムアウト | 未取得 |
| 基点、120 回更新、取り出しだけインデックスへ変更 | 145,200 | 74.9 ms | 227.2 ms | 11.8 ms |
| 修正後、120 回更新 | 1,200 | 0.2 ms | 906.9 ms | 7.9 ms |

タイムアウト時、診断でレンダラープロセスの CPU 時間は約 27.0 秒だった。
インデックス比較では基点の `pending.shift()` を `pending[cursor++]` に、ループ条件と
先頭参照を対応するカーソル方式に置き換えただけで、重複項目と世代チェックは残した。
この一時的な診断変更は出荷テストには残していない。配列の先頭削除と大量の同期スキップが
この再現の停止を支配することを裏付ける。実機で発生した停止がすべてこの経路だったとは
断定しない。数値はいずれも単一実行の診断値で、性能保証ではない。

修正後の合計時間には意図的なタスク分割とタイマー待ちが含まれる。合計完了時間よりも、
キューの件数、要求並列数、入力を処理できる機会が残ることを回帰判定に使う。

## 修正内容と周辺経路

- 待機項目は弱参照ハンドルをキーとする Map に集約し、一つの非同期 consumer だけで
  処理する。描画フレームを待たずタイマーで開始する。revision 通知は dirty フラグに
  まとめ、レジストリ走査自体も重複させない。
- 生存確認・切断された範囲の破棄も含め、128 項目または 8 ms ごとに別タスクへ譲る。
  新しい本文の追加時にも掃除するため、revision が動かない会話切り替えでも死んだ
  レジストリ項目を残し続けない。応答適用には世代と revision epoch を照合し、
  同じ装飾結果なら DOM を変更しない。
- health 応答を保留して復帰通知を 100 回送ると、従来は 100 要求が並列に開始された。
  health の初回・定期・復帰・SSE フォールバックを一つの flight にまとめ、実行中に
  届いた通知には後続一回で対応する。復帰前の成功応答も `unreachable.gen` で捨てる。
- health のネットワーク待ちには 15 秒の期限を置く。会話優先処理による待機中も
  中止可能にし、待機リストと abort リスナーを回収する。会話描画後の優先権解放には
  250 ms のフォールバックを設け、止まった rAF だけを待ち続けない。

SSE は既存の一つの EventSource を再利用し、error のフォールバックタイマーも既に一つに
制限されていた。切断のたびに EventSource を作り直す変更はしていない。
`loadStore` の差分連結・全件取得への切り替えと `sectionRequest` の後続取得は維持した。
会話本文は既に内容のキーで DOM 再構築を抑制していた。今回の 300 ターンの検証では
本文 DOM の再構築が支配的な負荷という証拠はなく、履歴描画方式は変更していない。
待機表示には既存の共有タイマーがあり、休止中の秒数を一回ずつ再生するループはない。

## 回帰検証

```sh
node --test tests/web_progressive.mjs tests/web_list_progressive.mjs tests/web_questions_progressive.mjs
RUSTUP_TOOLCHAIN=stable cargo test --locked --test web_render -- sleeping_reference_backlog_stays_bounded unreachable_banner_waits_out_transient_failures linkify_builds_anchors_and_keeps_markup_as_text --nocapture
RUSTUP_TOOLCHAIN=stable cargo clippy --locked --test web_render -- -D warnings
```

ブラウザ回帰テストは実装の参照処理を実 DOM 上で実行し、1,200 範囲・120 更新、
停止した rAF、切断された 5,000 範囲の掃除を扱う。別途、実 API で読み込んだ 300 ターンの
会話を開き、health を保留した状態で時計を 8 時間進め、復帰・pageshow・SSE error と
change を各 100 回送る。health の並列数 1、要求数 2、最新状態への収束、古い成功応答の
不採用を確認する。下書き、編集中の入力、フォーカス、選択範囲、返信先、添付、選択した
会話、スクロール位置、行と本文の同一性を確認する。テストの初回自動スクロールは
reduced-motion で即時完了させ、復帰による移動と混同しない。

ある実行では会話本文の要素数は前後とも 4,200、GC 後の document 数は前後とも 1、
イベントリスナーは 605 → 608 だった。後者は返信・添付コントロール追加を含む。
これはこのバーストでの無制限な増殖を否定する確認であり、長期間の全リソースに
リークがないという証明ではない。JavaScript の制御テストでは保留通信中の世代更新、
会話切り替え後の遅延応答、フレーム停止時の優先権解放、要求中止時の待機解除も検証する。

対象の JavaScript テスト 78 件とブラウザテスト 3 件、および対象 integration target の
Clippy が成功した。全体テストと最終 gate は親グラフが担当する。

## 手動確認と残る不確実性

長い会話で下書きと返信先・添付を設定し、途中の本文へスクロールする。別タブへ移り、
休止・復帰またはネットワーク切断・再接続を行い、更新中も入力・会話選択が動作し、
下書き等を保ったまま最新の会話へ収束することを確認する。

今回、実際の OS 休止、Brave 固有の省電力・拡張機能・GPU の影響は再現していない。
報告環境で停止が続く場合は停止中のレンダラープロファイルが必要になる。
巨大な単一メッセージの Markdown 描画や、全履歴を DOM に保持する費用自体は残る。


## 非表示中の参照更新の保留

参照更新は非表示中に新しいタイマーを予約せず、保留済みの弱参照と更新フラグを維持する。
`visibilitychange` で表示に戻った時だけ、既存の単一コンシューマーを再開する。
非表示になる前に予約されたタイマー、走査中の協調的な中断、通信中の表示切り替えでも、
未処理範囲を残して後続バッチを保留する。既に開始した通信の応答は従来どおり世代を検証する。

この動作は `tests/web_progressive.mjs` の `node:vm` テストで、非表示中の 300 範囲・
200 回の更新通知、表示通知の重複、予約後・走査中・通信中の非表示化を検証する。
追加のパッケージやブラウザ環境なしで実行できる。既存の実ブラウザによる検証も維持する。

追加後の確認では `node --test tests/web*progressive.mjs` の 83 件と、
`RUSTUP_TOOLCHAIN=stable cargo test --locked --test web_render sleeping_reference_backlog_stays_bounded -- --nocapture`
の 1 件が成功した。全体テストと最終 gate は親グラフが担当する。
